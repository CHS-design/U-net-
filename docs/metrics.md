# 分割指标说明：mIoU 与 mAcc

本文档说明本项目多类语义分割（PlantSeg 植物病害分割，115 类病害 + 背景）所用的两个核心指标 **mIoU**（mean Intersection over Union，平均交并比）和 **mAcc**（mean Accuracy，平均像素准确率/召回率），以及它们在代码中的具体实现。

**本文档是自包含的**：第 1、2 章讲原理，不需要任何代码背景；第 3～5 章讲实现，每段代码都配了"用大白话说"的解释和一个手算示例，即使不打开源码也能理解。所有实现集中在 `utils/metrics.py`，训练、验证、测试、推理共用同一套逻辑。

---

## 0. 阅读前提：符号与术语约定

下表把全文会用到的"黑话"先解释清楚。如果你不熟悉深度学习，读第 1、2 章前先看这里。

| 符号 / 术语 | 含义（大白话） |
|---|---|
| **像素** | 图像的最小单位。一张 512×512 的图有 26 万多个像素，分割任务要给**每个像素**分配一个类别 |
| **C** | 类别总数。本项目 C = 116（115 类病害 + 1 类背景） |
| **B / H / W** | 一批图像的张数（Batch）、高（Height）、宽（Width）。`(B,C,H,W)` 表示"这批有 B 张图，每张 C 个通道、H 行 W 列" |
| **logits（模型输出）** | 模型对每个像素、每个类别打的一个"分数"。可以想象成一张分数表：某个像素属于病害A几分、属于病害B几分、属于背景几分 |
| **target（真实标签）** | 人工标注的正确答案，每个像素一个类别编号（0=背景，1~115=各类病害） |
| **argmax** | "取分数最高的那个类别"这个动作。把分数表变成一张"每个像素的预测类别图" |
| **TP / FP / FN** | 真正例（真属该类且预测该类）/ 假正例（不属该类却预测该类）/ 假负例（属该类却没预测出来）。漏检=FN，误检=FP |
| **GT** | Ground Truth 的缩写，即真实标签中某类的像素总数，等于 TP + FN |
| **混淆矩阵** | 一张 C×C 的表，第 i 行第 j 列记着"真实为类 i、却被预测为类 j"的像素个数。对角线是预测正确的 |
| **split（数据集划分）** | train（训练）/ val（验证，用于调参选优）/ test（测试，只在最后评估用一次） |
| **present（类）** | "在真实标签中出现过的类"。某类若在整个验证集里一个像素都没有，就不是 present |

有了这些约定，下面开始。

## 1. 指标定义与用途

### 1.1 IoU（交并比）

对单个类别 \( c \)：

\[
\mathrm{IoU}_c = \frac{TP_c}{TP_c + FP_c + FN_c}
\]

其中 \( TP_c \) 是真实为 \( c \) 且预测为 \( c \) 的像素数，\( FP_c \) 是预测为 \( c \) 但真实不是的像素数，\( FN_c \) 是真实为 \( c \) 但预测不是的像素数。分母正是"真实集合与预测集合的并集"——直观理解：**你圈出的区域和正确答案圈出的区域，重叠部分占两者合起来总面积的比例**。

### 1.2 mIoU（平均交并比）

\[
\mathrm{mIoU} = \frac{1}{N_c}\sum_{c=1}^{N_c} \mathrm{IoU}_c
\]

对所有类别的 IoU 取算术平均。它同时惩罚"漏检"（FN）和"误检"（FP），是语义分割领域最核心的评价指标（PASCAL VOC、Cityscapes 等基准均以它为主排名）。

### 1.3 Acc（逐类像素准确率 / 召回率）

\[
\mathrm{Acc}_c = \frac{TP_c}{GT_c}
\]

其中 \( GT_c \) 是真实标签中类别 \( c \) 的像素总数。它只关心"真实属于该类的像素有多少被正确找出"，等价于该类的召回率（Recall），**不看误检**——即使你把很多健康组织误判成病斑，只要真实病斑都找全了，这个类的 Acc 就高。

### 1.4 mAcc（平均像素准确率）

\[
\mathrm{mAcc} = \frac{1}{N_c}\sum_{c=1}^{N_c} \mathrm{Acc}_c
\]

对所有类别的逐类准确率取平均。它补充了 mIoU 的视角：当某个稀有类几乎没被检出时，即使它没有误检（IoU 分子分母都小），mAcc 也会明确暴露问题。

### 1.5 两者的分工

| 指标 | 关注点 | 对误检 FP 的敏感 | 典型用途 |
|---|---|---|---|
| **mIoU** | 预测区域与真实区域的整体重叠 | 敏感 | 主排名指标、选优/早停依据 |
| **mAcc** | 每类真实像素被找回的比例 | 不敏感 | 辅助诊断稀有类召回情况 |

## 2. 为什么选择 mIoU 和 mAcc

### 2.1 契合分割任务而非单纯分类

像素级分割要求同时做到"定位正确"和"边界准确"。整体像素准确率（Pixel Accuracy，即"所有像素里猜对的比例"）会被大面积背景主导——即使模型偷懒把所有像素都预测成背景，也能拿到约 80% 的像素准确率（本项目 PlantSeg 背景占约 81% 像素，这个数字来自项目对训练集掩膜的统计）。mIoU 和 mAcc 都按**类别**平均，让每个类别（无论面积大小）对最终分数有同等权重，避免了背景主导的假象。

### 2.2 对类别不平衡的敏感度

PlantSeg 有 115 类病害，类间像素数差异极大（以下数字均来自项目对数据集的实际统计，详见 `EXPERIMENTS.md`）：

- 背景类占约 81% 像素；
- 稀有类（如类别 69）在整个训练集只出现在 4 张图上；
- 部分类别在某个 split 中完全缺失（val 缺 69，test 缺 42）。

在这种极端不平衡下：

- **mIoU** 对每个类公平计权，稀有类表现差会直接拉低总分，能反映模型是否真的学会了少数类；
- **mAcc** 直接衡量每类的召回，能诊断"模型是否忽略了某类"（本项目训练初期模型塌缩为"全预测背景"时，mAcc 卡在 0.0087，精准暴露了问题——即便不看代码，这个接近 0 的数值也说明几乎没有病斑被找回）。

相比之下，全局像素准确率在这种场景几乎失去分辨力——这也是本项目日志不打印全局 acc、而打印 mIoU/mAcc 的原因。

### 2.3 与实际业务目标的契合

植物病害分割的业务价值在于**准确识别并勾画病斑**，尤其是早期、小面积病斑：

- 漏检一个病斑（FN）在农业场景下代价高（错过防治时机）→ mAcc 直接反映召回；
- 误检健康组织为病斑（FP）会导致误施药 → mIoU 同时惩罚 FP；
- 两者结合，既要看重叠质量（mIoU），也要看少数类是否被召回（mAcc）。

### 2.4 与主流论文对齐

STAR-Net 论文（PlantSeg 数据集）和其他分割工作统一用 mIoU 作为主指标、mAcc 作为辅助，本项目采用同一标准，便于横向对比（见 `EXPERIMENTS.md` 第 6 章）。

## 3. 当前代码的计算方式与逻辑（无需源码也能读懂）

实现集中在 `utils/metrics.py`。核心链路用一句话概括：

> 每一批图像预测完后，把"真实类别 vs 预测类别"累计进一张混淆矩阵；需要出指标时，从这张表里算出每个类的 IoU 和 Acc，再在"出现过的类"上取平均，得到 mIoU 和 mAcc。

下面逐段拆解，每段先讲"在做什么"，再给代码片段佐证。代码对应函数为
`MultiClassMetricTracker.update()` → `multiclass_confusion()` → `multiclass_scores()` → `compute()`。

### 3.1 预测类别的获取（后处理）

**用大白话说**：模型给每个像素输出的是"各类分数"（logits）。我们不需要先把分数换算成概率（softmax），直接挑分数最高的类别，作为这个像素的预测结果。挑最高分这件事就是 `argmax`——因为无论是否换算成概率，最高分对应的类别不变，所以省掉 softmax 这一步。

```python
pred = logits.argmax(dim=1)   # 输入 (B,C,H,W) 分数表 -> 输出 (B,H,W) 类别编号图
```

这与 `predict.py` 推理时生成分割图用的是完全相同的动作，保证"评估时怎么算类别"和"实际预测时怎么算类别"一致。

### 3.2 混淆矩阵的构建

**用大白话说**：建一张 C×C 的空表 `conf`，遍历所有像素，看到"真实是类 i、预测是类 j"，就在 `conf[i][j]` 这一格加 1。最后对角线上的数就是每类预测正确的像素数（TP）。

```python
target = target.long()
valid = (target >= 0) & (target < num_classes)   # 忽略越界标签
idx = target[valid] * num_classes + pred[valid]  # 把 (真实,预测) 二维坐标压成一维
conf = torch.bincount(idx, minlength=num_classes**2).view(num_classes, num_classes)
```

三个关键点：

- **忽略标签处理**：`valid` 这行排除两类非法标签——负数（有些数据集用 -100 表示"这里不要算"）和大于等于类别总数的越界值。这些像素既不贡献正确数也不贡献错误数，完全不参与统计。
- **坐标压平**：一张二维表用一维下标访问更快。把坐标 `(真实 i, 预测 j)` 编码成 `i × C + j`，用 `bincount`（一次性统计一堆整数各出现几次）算出所有格子，再 `view` 回 C×C 的形状。这比写两层循环逐格统计高效得多。
- **跨 batch 累计**：验证集有上千张图，不可能一次全塞进显卡。所以每处理一小批（batch）就把它的混淆矩阵累加到 `self.conf` 这张总表上，直到所有图都过一遍。统计量一直留在 GPU 上，只在最后算指标时才取回 CPU——避免频繁搬运数据拖慢速度。

### 3.3 一个手算小例子（把上面两步串起来）

假设只有 2 类（0=背景，1=病害），一张图 3 个像素：

- 真实标签：`[背景, 病害, 病害]` 即 `[0, 1, 1]`
- 模型预测：`[背景, 病害, 背景]` 即 `[0, 1, 0]`（第三个病斑漏检了）

第一步，数混淆矩阵 `conf[真实][预测]`：

- 像素1：真实0、预测0 → `conf[0][0] += 1`
- 像素2：真实1、预测1 → `conf[1][1] += 1`
- 像素3：真实1、预测0 → `conf[1][0] += 1`

得到：

\[
conf = \begin{bmatrix} 1 & 0 \\ 1 & 1 \end{bmatrix}
\qquad
\text{（行=真实，列=预测）}
\]

第二步，从表里取数：

| 量 | 怎么从 conf 得到 | 结果 |
|---|---|---|
| `inter[c]`（该类 TP，对角线） | `conf[0][0]`, `conf[1][1]` | `[1, 1]` |
| `gt[c]`（该类真实像素数，行和） | 第0行 `1+0=1`，第1行 `1+1=2` | `[1, 2]` |
| `pred[c]`（该类被预测数，列和） | 第0列 `1+1=2`，第1列 `0+1=1` | `[2, 1]` |
| `union[c]`（并集） | `gt + pred - inter` | `[2, 2]` |

第三步，逐类算指标：

- 背景类：IoU = 1/2 = 0.5，Acc = 1/1 = 1.0
- 病害类：IoU = 1/2 = 0.5（注意第 3 个像素既算 FN 也算 FP），Acc = 1/2 = 0.5（漏掉的那个病斑拉低了召回）

第四步，两类都出现过，都参与平均：

\[
\mathrm{mIoU} = (0.5 + 0.5)/2 = 0.5
\qquad
\mathrm{mAcc} = (1.0 + 0.5)/2 = 0.75
\]

可以看到：**mAcc 高于 mIoU**，因为 mAcc 没惩罚"把背景误判成病害"这个 FP，而 mIoU 惩罚了。这正是两个指标互补的体现。

对应的代码就是：

```python
inter   = torch.diag(conf)        # 对角线：每类 TP
gt      = conf.sum(dim=1)         # 行和：每类真实像素数
pred    = conf.sum(dim=0)         # 列和：每类被预测数
union   = gt + pred - inter       # 并集 = GT + Pred - TP
```

### 3.4 类别平均方式（present 掩码）

**用大白话说**：算完所有类的 IoU/Acc 后，不对"全部 116 类"取平均，而是只对"真实标签里实际出现过的类"取平均。因为有些类在整个验证集里一个像素都没有（比如本项目 val 集缺类别 69），把它们算进去等于用一堆"分母为 0 的类"稀释结果，没有意义。

```python
present = gt > 0
iou = (inter + eps) / (union + eps)
acc = inter / (gt + eps)
miou = iou[present].mean()
macc = acc[present].mean()
```

这也是语义分割的通行做法（PASCAL VOC 等基准同样跳过未出现的类），保证不同数据集划分下的指标可比。

### 3.5 分母为零的处理

**用大白话说**：除法最怕分母为 0。代码在分母上加一个极小的数 `EPS = 1e-6`（百万分之一），避免算出无穷大或报错。mIoU 的分子也加，是为了防止极端情况下出现 0/0。

- IoU：\( \dfrac{TP_c + \varepsilon}{union_c + \varepsilon} \)
- Acc：\( \dfrac{TP_c}{GT_c + \varepsilon} \)

由于上一步已排除 `gt = 0` 的类，对参与平均的类而言分母必然大于 0，`EPS` 主要起数值稳定作用。但如果某类真实出现过、模型却一个像素都没预测对（`inter = 0`），它的 IoU 就是 0——**不会被这个极小值抹平**，会真实拉低 mIoU，这正是指标应有的行为。

### 3.6 训练时如何用它选最优模型

**用大白话说**：训练每一轮结束后都在验证集上算一次 mIoU。如果这一轮的 mIoU 比历史最高还高，就把当前模型存为 `best.pt`；如果连续 20 轮都没创新高，就提前停止训练。这样做是为了让"挑出来的最佳模型"和"最终评价用的指标"是同一个东西，避免loss最低但分割效果并非最好的情况。

```python
keys, key = metric_keys(), select_key()   # 多类任务: keys=["miou","macc"], key="miou"
...
if val_metrics[key] > best_score:          # val mIoU 创新高才保存 best.pt
    ...
```

- 多类任务监控 **mIoU**（与评价指标对齐，比 loss 更能反映分割质量）；二值任务监控 **Dice**
- `PATIENCE=20`：连续 20 轮不创新高才早停——因为 115 类冷启动慢，给足时间爬升（设为 5 时模型会在学会之前就被停掉）

### 3.7 数据加载侧的标签校验

**用大白话说**：在把标注图喂给模型和指标计算之前，先检查一遍类别编号是否都在合法范围（0 到 115）内。如果有越界的编号，立即报错。这样从源头保证统计可信——相当于"入口安检"，与 3.2 中计算时的 `valid` 掩码形成"双重保险"。

```python
validate_labels(raw_mask, cfg.NUM_CLASSES, source=f": {mask_path}")
```

CE 损失和 mIoU/mAcc 都要求标签合法；这个校验在 `utils/data.py` 加载掩膜时调用，与指标模块共用同一个规则。

## 4. 二值任务的对应实现（对照）

二值任务（如 Oxford-IIIT Pet 的前景/背景分割）用 `BinaryMetricTracker`，指标不同但设计思路一致：

| 二值指标 | 公式 | 说明 |
|---|---|---|
| Dice | \( 2I/(P+G) \) | \( I \)=交集，\( P \)=预测前景，\( G \)=真实前景；选优依据 |
| IoU | \( I/(P+G-I) \) | 交并比 |
| Acc | 正确像素 / 总像素 | 全局像素准确率 |

二值版同样在 GPU 上异步累计、在 `compute()` 时一次性同步，与多类版共享 `EPS` 和"全局统计"的思路。区别仅在于：二值是前景/背景两类、用 sigmoid + 阈值（默认 0.5）得到硬掩膜；多类是 C 类、用 argmax 得到类别索引图。

## 5. 模块接口速查（面向开发者）

> 本节是给需要改代码或复用模块的开发者查阅的 API 清单。**不读本节不影响理解前面的原理。**

| 接口 | 用途 |
|---|---|
| `multiclass_confusion(logits, target, C, device)` | 构建混淆矩阵（供复用/可视化） |
| `multiclass_scores(conf)` | 返回逐类 + 均值统计量（tensor，未同步） |
| `validate_labels(target, C, source)` | 标签合法性校验（数据加载调用） |
| `MultiClassMetricTracker(device, C)` | 多类跨 batch 累计器，`compute()` 返回 `{miou, macc}` |
| `BinaryMetricTracker(device)` | 二值跨 batch 累计器，`compute()` 返回 `{dice, iou, acc}` |
| `build_metric_tracker(device)` | 工厂：按任务类型创建对应累计器 |
| `metric_keys(task)` / `select_key(task)` | 元信息：日志键名 / 选优键 |

调用位置：

- `train.py`：训练和验证时用工厂创建累计器，用元信息函数生成日志表头与选优
- `evaluate.py`：测试时复用同一个评估函数，间接复用同一套指标统计
- `utils/data.py`：加载侧调用标签校验
- `predict.py`：推理的 argmax 后处理与指标侧的预测逻辑一致

## 6. 一致性验证说明

把指标逻辑集中到统一模块后，用固定随机种子（42）对 4 类和 116 类、正常标签/越界标签/单类三种场景做了数值对比，mIoU 与 mAcc 在重构前后**逐位一致**（差异 < 1e-12），确认结构整理没有改变任何计算行为。这说明本文档描述的计算逻辑与实际运行代码严格对应。
